# Forge 8.23.0

Forge 8.23.0 adds an application-owned composition phase for connecting
long-lived process-local services after plugins initialize and before they
start. Applications can now consume plugin APIs, construct a runtime client and
publish that exact client type without introducing a plugin whose only purpose
is service registration.

This is an additive App release over Forge 8.22.0. Chain, P2P, transport, wire
and persisted-storage contracts do not change.

## Application Connect Services

`application_builder::connect(...)` accepts synchronous or asynchronous
callbacks. A `connect_context` reads the existing local API registry through
`api<Interface>()`, publishes one non-null `shared_ptr<T>` for each exact type
and lets later connect callbacks consume previously published services.

The shell freezes publication before the application `after_initialize` hook
and plugin startup. Plugins retain a copyable `service_view` from
`plugin_context::services()` during initialization and perform lock-free local
lookups during startup and normal operation. The application and foreground
owner can use `application_context::service<T>()` and
`application_shell::services()` respectively.

The lifecycle order is now:

```text
provide APIs
initialize plugins
connect application services
run application after_initialize
startup plugins
shutdown plugins in reverse order
destroy connected services
```

Connect failure closes publication, preserves the original typed exception,
rolls back initialized plugins and destroys services only after plugin
shutdown. Null, missing, duplicate and late publication use dedicated
`forge.app` typed errors.

## Compatibility

Existing applications require no source migration. The previous
`application_context` and `plugin_context` constructor forms remain available;
they create an empty service view. Applications that need connected clients can
adopt the new builder phase directly:

```cpp
builder.connect([](forge::app::connect_context& context)
   -> boost::asio::awaitable<void> {
   auto resolver = context.api<resolver_api>();
   context.publish(co_await make_client(*resolver));
});
```

The registry is not a dependency-injection container: it has no factories,
named services, scopes, replacement or automatic wiring. Reconnect and peer
selection remain responsibilities of the published client.

## Validation

Focused App coverage verifies callback ordering, API consumption, exact-type
publication, concurrent immutable reads, typed failures, rollback, idempotent
lifecycle and service destruction after plugin shutdown. Installed App export
metadata includes the new `forge.app.connect_context` and
`forge.app.service_registry` modules.
