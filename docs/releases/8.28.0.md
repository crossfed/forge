# Forge 8.28.0

Forge 8.28.0 is the minor release for the net change from `v8.27.1` through
`11ea68ac`. It contains maintainer-approved pre-stabilization clean breaks in
public source, package and versioned Chain API contracts. There are no
compatibility aliases, forwarding modules, deprecated aggregate targets, old
readers or alternate JSON modes for the replaced surfaces.

## Native Admin Foundation

Forge now provides the neutral foundation for a native C++ backend serving a
browser administration application: shared TLS context rotation and native
HTTPS, bounded static assets and HTTP cookies, plus pairing, session and
browser-authentication state machines. `forge.auth.pairing`,
`forge.auth.session` and `forge.auth.http` keep owner pairing, browser sessions
and cookie/CSRF policy separate from product authorization and signing policy.
The foundation does not by itself make a downstream deployment production-ready.

The following Stable HTTP source changes are an explicitly approved
pre-stabilization break:

| Before | After |
| --- | --- |
| `response.set_cookie(name, value)` | `forge::net::http::append_set_cookie(response, forge::net::http::set_cookie{.name = name, .value = value})` |
| `file_response::from_path(path, options)` | Insert the caller-owned `forge::asio::compute::pool::get_executor()` before `options`. |
| `static_file_root(root, options)` | Insert the caller-owned `forge::asio::compute::pool::get_executor()` before `options`. |

No cookie or file-executor compatibility overload remains. Product integrations
must make the executor ownership explicit and use the cookie helper.
`router::mount_assets` is new in 8.28.0 rather than a replacement for an
older router API. Low-level callers either pass their executor explicitly as
`router::mount_assets(asset_mount, executor)`, or pass a prebuilt
`asset_bundle` with `router::mount_assets(asset_bundle)`. The first form leaves
bounded file-read executor ownership with the caller; the second preserves the
executor already owned by the bundle. The HTTP Server plugin uses its
application `context.compute()` executor when it turns an `asset_mount` into
that bundle.

`forge.plugins.http.server` moves from contract 1.0 to 2.0. Resolve the API at
major 2. Every custom `forge::plugins::http::server::api` implementation must
add the new pure virtual operations
`mount_assets(forge::net::http::asset_mount)` and `reload_tls()`; callers use
those operations to publish bounded assets and reload fully resolved TLS
identity material. There is no 1.0 compatibility implementation.

Only host tooling moves. Guest `forge::contract` remains the Contract SDK

The concrete WASM backend receives the same clean split:

| Before | After |
| --- | --- |
| `libraries/vm/wasm`, `forge_vm_wasm`, `Forge::forge_vm_wasm`, `vm_wasm` | `libraries/vm/wasm/interpret`, `forge_vm_wasm_interpret`, `Forge::forge_vm_wasm_interpret`, `vm_wasm_interpret` |

validation, execution, host-function ABI, SoftFloat and donor mapping do not
change, and Forge does not retain a `forge_vm_wasm` aggregate or alias.

## Chain State Projections and API Breaks

`forge.chain.protocol` now provides typed native state projections, named
guest-safe IDs and selectors. Migrate the former
`forge.chain.protocol.typed_id` template to `forge.db.ids.typed_id`; consume
named protocol IDs through `forge.chain.protocol.native_ids`. Host generic
object-ID conversion remains in `forge.db.ids.object_id`. Exact selection uses
`forge.chain.protocol.entity_selector`; `account_selector` is its public alias
for an `account_id` or `account_name` selector.

`forge.db.ids.typed_id` no longer has an `object_id` constructor or
`as_object_id()`. Host code that converted a generic ID must call
`try_typed<Space, Type>(object)` and handle the empty result; code that emitted
a generic ID must call `to_object_id(typed)`. Both helpers are in
`forge.db.ids.object_id`; the guest-safe `forge.db.ids.typed_id` module remains
free of generic object-ID conversion.

The transport contracts are a clean break:

| Previous contract | 8.28.0 contract and required migration |
| --- | --- |
| `forge.chain.api.state` 2.0 | `forge.chain.api.state` 3.0 keeps the typed state method family but replaces its selectors, routes and canonical DTOs as described below; regenerate every remote binding and fixture. |
| `forge.chain.api.block` 1.0 | `forge.chain.api.block` 2.0. Regenerate clients for canonical activated-feature, chain-config, WASM-parameter, producer and finalizer records. |
| `forge.chain.api.info` 1.0 | `forge.chain.api.info` 2.0. Use canonical `resource_config` and `resource_state` instead of the removed duplicated CPU/NET and total-weight fields. |
| `forge.chain.api.admin` 1.0 | `forge.chain.api.admin` 2.0. Consume canonical `account_ram_correction` records. |

For State 3.0, migrate `account_request` and `code_request` from one
`account_name` to the `account_selector` `id`/`key` choice. Their HTTP routes
move from `/v1/chain/state/accounts/{account}` and
`/v1/chain/state/accounts/{account}/code` to
`/v1/chain/state/accounts?id={id}&key={key}` and
`/v1/chain/state/codes?id={id}&key={key}`. Rename `include_code` to
`include_wasm`, and consume `code_response.code`, `wasm` and `abi` instead of
the former account/hash/ABI fields. State 3.0 also adds
`get_permission_links(permission_links_request)`, served at
`GET /v1/chain/state/permission-links` with `id`, `key`, `code`,
`message_type`, `limit` and opaque `cursor` query fields.

Replace the former account-state response and mutation values with canonical
`full_account` and optional `account_authority`; use `table_name` rather than
generic `name` for table selectors and scope requests, canonical `table` rows
in table-scope responses, and canonical `currency_stats` in currency-stats
responses. Scheduled transactions now use canonical `generated_transaction`,
optional time bounds and opaque byte cursors instead of JSON mode, string
lower bound and `time_limit_ms`; authorizer continuations are likewise opaque
bytes rather than `authorizers_cursor`.

These Chain API major versions change the remote DTO, Raw and JSON contracts.
Rebuild and regenerate every client, proxy and stored fixture that consumes
them; a current endpoint does not read the removed shapes. The protocol library
does not ship a controller or a persisted-store migration. Its projections
describe canonical records, so product owners must make any controller-store
migration explicitly rather than relying on an old Forge reader.

Nested Raw values now use exact bounded frames and share the parent cumulative
container budget. Aggregate Raw serialization is supplied centrally through
Boost.PFR field traversal for eligible aggregates, replacing duplicate local
`raw_pack`/`raw_unpack` overloads without creating a second legacy encoding.
Field order remains the declared canonical order.

## API and P2P Work Already in `dev`

The net release range also includes trusted server-supplied invocation fields:
clients clear them before serialization, while server bindings fill them only
from immutable trusted invocation metadata and fail closed when a required
value is unavailable. P2P API publication now returns the move-only
`forge::api::p2p::publication` ownership handle; local node and resolver API
contracts move from major 1 to major 2, and callers retain that handle for the
lifetime of the publication.

The current P2P topology implementation is already in `dev`, including the
managed/static-only topology policy, bounded DHT, rendezvous and peer-exchange
work. It contains the following Stable low-level source breaks, which require
mechanical migration rather than a compatibility layer:

| Before | After |
| --- | --- |
| One DHT configuration in `node::limits::dht` | Configure one or more `node::options::dht_profiles`; create the selected `dht::profile` with `amino_v1(...)` or `custom_dht_profile(...)`. Plugin configuration uses `dht.profiles` entries. |
| `dht::options::max_message_size` | Set both `dht::options::max_outbound_message_size` and `max_inbound_message_size` explicitly. |
| `node.routing_status()` | Select the profile: `node.routing_status(profile)`. |
| `co_await node.async_find_peer(peer)` | `co_await node.async_find_peer(profile, peer, query_options)`. |
| `co_await node.async_provide(key)` | Retain `auto registration = co_await node.async_provide(profile, key, query_options)`. The move-only `provider_registration` owns that publication; keep it alive and use `async_withdraw()` for orderly withdrawal. |
| `co_await node.async_find_providers(key)` | `co_await node.async_find_providers(profile, key, query_options)`. |

The profile is now the DHT protocol and capability boundary. It owns the DHT
mode, peer/provider/value capabilities, limits and value policies, so callers
must not rely on an implicit single-node DHT. This release metadata documents
the existing P2P implementation only; it does not alter P2P source.

Provider persistence is also profile-scoped. Migrate the removed
`peer_store::provider_record` and the provider fields of
`peer_store::mutation_batch`, `hydration_page` and `prune_result` to their
`dht::record_store` counterparts. The DHT mutation batch now has explicit
provider upserts and removals, while its prune result carries provider keys and
provider-address updates. Replace `peer_store::hydration_kind::providers` with
`dht::record_store::hydration_kind::providers`,
`peer_store::options::max_providers` with the selected profile's
`dht::record_store::options::max_providers`, and the removed
`peer_store::async_upsert_provider()` / `peer_store::find_providers()` with
the corresponding `dht::record_store` operations.

Each profile receives a `dht::record_store::persistence` implementation through
the `protocol_id` keyed `node::options::dht_record_persistence` map; do not put
DHT provider rows back into `peer_store::persistence`. Add that same profile
`protocol_id` as the first argument to `peer_store::upsert_routing_peer(...)`.
`capabilities::dht` is removed: declare the selected profile's explicit
`dht::profile_capabilities` (`peers`, `providers` and `values`) instead.

## Contract SDK Closure

The guest foundation archive graph now builds `forge.db.ids.typed_id` before
the Chain Protocol archive and includes the guest-safe protocol modules through
`native_ids`, `entity_selector` and `code`. The same modules are represented in
the package and install manifests. The installed EOSIO serialization veneer
also declares aligned allocation before importing the Raw codec, so standard
library containers of over-aligned protocol values compile from the SDK surface.

ABI fixtures verify that the public `account_selector` alias resolves
deterministically to its generated entity-selector record. This closure changes
Forge-owned guest build and validation surfaces only. The pinned Spring/CDT
donor corpus remains unchanged and is still a compatibility oracle, not a
released SDK dependency.

## Validation

The scoped Chain Protocol/API acceptance used Homebrew LLVM 22.1.8, Ninja and
`RelWithDebInfo`. It passed its relocation consumers and relevant typed API,
HTTP, stream, QUIC, WebSocket, P2P and DB IDs consumers; the recorded
acceptance boundary is in
[`forge-chain-protocol-state-projections-v1-local-acceptance.md`](../iterations/forge-chain-protocol-state-projections-v1-local-acceptance.md).

The final Contract SDK acceptance used the same toolchain with `Release` host
and guest configurations. It passed:

- the `contract-sdk-host` build and `forge_tooling_testing_check`;
- developer SDK archive, task-local install and relocation;
- the complete 484-step installed-SDK consumer and tooling fixture build;
- generated-contract execution in Forge VM;
- canonical ABI, hash and import parity for ten unchanged Spring/EOSIO corpus
  contracts, followed by their Forge VM E2E test.

The focused typed-control gate also passed with:

```bash
python3 tests/chain_api/check_typed_control_surfaces.py .
```

The guest archive gate checks typed-ID ordering and the
`native_ids`/`chain_config` module presence. The exact feature diff received a
clean local Sol review after the Contract SDK findings were fixed.

GitHub CI and Codex review were intentionally not run. The three unrelated
baseline failures documented in the acceptance note remain outside this
release scope; this is not a claim of a green unfiltered Forge suite.
