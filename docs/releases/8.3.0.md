# Forge 8.3.0

Forge 8.3.0 adds a bounded Asio compute pool, reorganizes the task scheduler,
adds DB Core savepoints and transaction participants, durable DB Revision
storage, optional Revision integration in the DB Store plugin and unified DB
Object/Blob read snapshots over one committed point in time.

This release also introduces explicit contract stability rules. Public
contracts are Stable by default. A library may allow documented source-level
changes in a MINOR release only when its owning README marks the affected API as
Preview or Experimental.

## Stability

The following source surfaces are Preview in Forge 8.x:

- Asio task and compute APIs;
- App scheduler and compute integration;
- DB Core savepoint, participant and record-lock extensions;
- DB Object public C++ API;
- DB Revision public C++ API;
- DB Store plugin C++ API and local API contract.

Source stability does not implicitly change wire or persisted storage
stability. Existing application object/index and blob record layouts are not
redefined by this release. Revision journal rows and blob retention barriers are
new records created only when Revision is explicitly enabled and joined.

## Source Migration From 8.1

The Asio task scheduler now follows the family namespace and module layout:

```cpp
// Forge 8.1
import forge.asio.task_scheduler;
forge::asio::task_scheduler scheduler{runtime};
forge::asio::task_handle handle = scheduler.submit(...);

// Forge 8.3
import forge.asio.task;
forge::asio::task::scheduler scheduler{runtime};
forge::asio::task::handle handle = scheduler.submit(...);
```

The remaining task names move in the same way:

- `forge::asio::priority` becomes `forge::asio::task::priority`;
- `forge::asio::task` becomes `forge::asio::task::task`;
- `forge::asio::task_context` becomes `forge::asio::task::context`;
- `forge::asio::awaitable_task` becomes `forge::asio::task::awaitable`.

App scheduler options and accessors now use
`forge::asio::task::scheduler`. Applications can opt into an owned compute pool
through `application_builder::compute(...)` or
`application_shell_options::compute`.

DB Object typed-ID lookup now belongs to the DB Object domain:

```cpp
// Forge 8.1
using index = forge::db::object::object_index_for_id_t<account::id_t>;

// Forge 8.3
using index = forge::db::object::index_for_id_t<account::id_t>;
```

`FORGE_DB_OBJECT(account_index)` keeps the same invocation. Code that manually
provided the inverse mapping must specialize
`forge::db::object::index_for_id<Id>` instead of
`forge::ids::type_for_id<Id>`.

Joining an Object store now waits for its writer lane and is asynchronous:

```cpp
// Forge 8.1
auto objects = store.join(tx);

// Forge 8.3
auto objects = co_await store.join(tx);
```

The same change applies to `plugins.db.store` Object handles. DB Object
transactions are move-only; pass them by reference when joining an existing
Object transaction and move them when transferring ownership.

## Bounded Asio Compute

- `forge.asio.compute` provides a bounded CPU execution pool outside the Asio
  runtime workers.
- Pending work and waiting submissions have separate limits, so native worker
  queues cannot become hidden unbounded storage.
- Cancellation is cooperative through `std::stop_token`; shutdown waits for
  running jobs and joins every compute worker.
- App ownership is opt-in. When configured, shutdown stops plugins, rejects and
  cancels queued scheduler work, drains compute while already-running scheduler
  continuations can still run, then drains the task scheduler and finally stops
  the Asio runtime. Scheduler drain is awaited without blocking the default
  single runtime worker.

## New DB Facilities

- DB Core transactions expose native savepoint create, rollback and release
  operations where supported by the backend.
- Transaction participants keep Object, Blob and Revision state synchronized
  with savepoint and outer transaction boundaries.
- `forge_db_revision` records before-images atomically with application changes,
  supports strict-head revert and bounded whole-revision pruning.
- Revision operations acquire the Object writer lane before locking persisted
  revision state; callers with Object mutations pass their joined Object
  transaction to the Revision store.
- `plugins.db.store` can enable Revision with `revision: {}` and explicitly join
  it to the same named-store transaction used by Object and Blob layers.

## Unified Read Snapshots

DB Core snapshots now carry driver-origin identity. DB Object and DB Blob stores
can join the same Core snapshot only when it is active and belongs to their
driver. This prevents accidentally composing one logical read from different
physical databases.

DB Blob adds a read-only snapshot with `get`, `has`, `stat_blob`, `verify` and
`ref_count`. The DB Store plugin exposes `store_handle::begin_read()`, returning
Object and Blob views over exactly one Core snapshot:

```cpp
auto read = co_await store.begin_read();
auto metadata = co_await read.objects().get(file_id);
auto payload = co_await read.blobs().get(metadata.content);
```

Snapshots opened before plugin shutdown remain valid until their last copy is
destroyed. Callers should keep them operation-scoped or bounded because native
snapshots retain old record versions and may retain RocksDB SST and Blob files.
