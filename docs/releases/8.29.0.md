# Forge 8.29.0

Forge 8.29.0 is the minor release for the net change from `origin/master`
(`bbd2a98739b4`) through `origin/dev` (`18c65dbc8a69`). It extends the native
Admin foundation released in 8.28 with TLS-capable HTTP clients, composed
OpenAPI documents and persisted pairing/session serialization. It also adds
declared plugin and snapshot lifecycle surfaces, canonical Raw bool stream
handling, and portable verified Chain reads backed by Savanna finality replay.

The only clean break in this release is explicitly limited to the unreleased
portable verified-client development API introduced within this release range.
Forge 8.28.0 did not ship that factory or its package-consumer surface. There
are no compatibility aliases or alternate trust-selection paths for the
replaced development surface.

## Native Admin Foundation

Forge 8.29 extends the 8.28 browser-facing Admin foundation with HTTP client
verification for hostnames and certificate pins, mutual TLS client identity,
bounded per-request credential headers, deterministic multi-interface OpenAPI
composition, and Raw serialization for pairing and session records. The
existing foundation keeps TLS, pairing, browser session and cookie/CSRF
mechanics separate from a product's authorization, signing and deployment
policy. It does not by itself make a downstream Admin deployment
production-ready.

The Chain Admin contract adds typed operator identity and node-status reads.
They are additive to `forge.chain.api.admin` 2.x. Existing Admin
implementations retain the default typed `unavailable` result until they choose
to implement the new operations; consumers must handle that outcome rather than
infer identity or status from an unrelated route.

## Plugin, Snapshot and Raw Contracts

Affected official plugin leaves now export lightweight descriptors alongside their
plugin contracts. Installed consumers can discover the declared plugin surface
without constructing plugin runtime state. This adds descriptor modules and
package coverage; it does not alter plugin lifecycle behavior.

`forge.chain.api.admin` advances from contract 2.0 to 2.3 with idempotent
snapshot requests and snapshot-status reads. A request is identified by its
caller-provided request ID, reports its lifecycle state, and can fail with the
typed `snapshot_lost` error when its anchor is no longer canonical.

Use the following lifecycle migration for callers that need a durable request
rather than the existing immediate `create_snapshot(name)` operation:

| Before | 8.29.0 migration |
| --- | --- |
| Start a snapshot with `create_snapshot(name)` and infer progress from product state. | Submit `request_snapshot(snapshot_request{.request_id = ..., .name = ...})`, retain the request ID, then poll `snapshot_status(snapshot_status_request{.request_id = ...})`. |
| Retry a failed request against an unknown head. | On `snapshot_lost`, obtain a current canonical head and submit a new request ID. Do not treat the lost request as completed or silently reuse its anchor. |

The Raw stream fix makes `bool` use the canonical one-byte encoding: `00` for
false and `01` for true. Canonical Raw wire and persisted bytes are unchanged,
so no reserialization or storage migration is required. Inputs that depended
on a noncanonical stream representation are invalid and must be corrected at
their producer.

## Portable Verified Chain Client

`forge.chain.api` now installs a portable verified-client closure:

- `forge.chain.api.verified_client_factory` builds a verified client from a
  caller-supplied `finality_verifier` and checks its declared trusted chain
  before the client can issue a raw request.
- `forge.chain.api.savanna_finality_verifier` is a thread-safe pimpl verifier
  that replays finality signatures, QC, policies, headers and validation from a
  caller-configured Savanna root or checkpoint. Successful verification
  automatically advances its preferred trust.
- `forge.chain.api.contract_table_projection_verifier` verifies contract-table
  rows and change projections against the authenticated state commitment.
- `forge.chain.protocol.contract_commitment` owns the portable table commitment
  keys and values used by that projection verifier.

The Savanna verifier retains configured roots plus the 16 newest promoted
rolling checkpoints for concurrent and historical replies. A response whose
witness bootstrap is no longer retained fails closed as
`forge::chain::api::exceptions::trust_required`; it must not be accepted by
selecting trust supplied by the server. A caller either retries from a retained
anchor or explicitly constructs a verifier with the required configured
root/checkpoint.

The wire DTOs, HTTP routes, finality-witness scheme
`spine.savanna.finality` version 1, and checkpoint Raw layout remain unchanged.
Rolling trust and replay-state caching are client-local memory only. Forge adds
no persisted trust-store format and no controller/store migration in this
release.

### Development API Migration

The following map applies only to consumers built from the intermediate dev
commits in this release range. It is not a migration requirement for a released
8.28.0 package consumer.

| Intermediate development surface | 8.29.0 surface and mechanical migration |
| --- | --- |
| `verified_client_options::trust` plus `additional_trusts` | Construct `auto finality = make_savanna_finality_verifier_with_trusts(trust, additional_trusts);` and pass it as `verified_client_options::finality`. A non-Savanna implementation may be passed instead when it declares the same trusted chain. |
| Factory-owned Savanna trust selection | The factory receives exactly one `std::shared_ptr<finality_verifier>`. Remove the second trust-selection path and retain the verifier for the lifetime of the client. |
| API-level `replay_savanna_finality_state(...)` | Hold `savanna_finality_verifier` and call `replay_state(expected_anchor, proof)`. This preserves the verifier's bounded request-safe replay cache. |
| Treat unavailable old bootstrap trust as a generic proof failure | Catch `trust_required`, then retry against a retained anchor or explicitly configure the required root/checkpoint. Do not weaken finality verification or accept server-selected bootstrap trust. |

The `chain_api` package component remains the installation entry point for
these modules. Regenerate intermediate package-consumer source checks against
the new factory shape; no package component name was removed.

## Validation Scope

The exact `origin/dev` release source was rechecked locally with Homebrew LLVM,
Ninja and `-j4`. The following 18 selected runtime, structure and installed
package tests passed:

- `test_forge_structure`, `test_forge_raw`, `test_forge_auth_pairing` and
  `test_forge_auth_session`;
- `test_forge_chain_api`, `test_forge_chain_portable_verified_client`,
  `test_forge_chain_api_typed_state_surface`,
  `test_forge_chain_api_portable_verified_client` and
  `test_forge_chain_api_typed_control_surfaces`;
- `test_forge_tls` and `test_forge_plugins_http_server`;
- `test_forge_package_auth_pairing_component`,
  `test_forge_package_auth_session_component`,
  `test_forge_package_chain_api_component`,
  `test_forge_package_chain_savanna_component`,
  `test_forge_package_plugins_descriptor_surfaces`,
  `test_forge_package_net_tls_component` and
  `test_forge_package_plugins_http_server`.

`test_forge_chain_api_spring_manifest` was skipped because that build did not
configure a donor source path.

The metadata-only version commit did not rerun the full unfiltered CTest suite
or GitHub CI. Those omissions are not represented as successful gates.
